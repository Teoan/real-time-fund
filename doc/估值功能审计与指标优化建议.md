# 估值功能审计与指标优化建议

> 审计范围：`app/api/fund.js` 中两条估值链路（实时估值 / 持仓穿透评分）+ `app/lib/valuationEngine.js`、`valuationRules.js`、`valuationHistory.js` + 相关 UI 与 hook。
> 审计方式：静态阅读 + 用 `node --input-type=module` 直接跑真实模块做数值验证（结论中的数字均可复现）。

## 一、结论速览

| #   | 问题                                                       | 严重度 | 影响                                                                 | 一句话改法                                               |

| 1   | 走势图末点与首屏分数不同源（序列丢弃 peg / dividendYield） | **P0** | 同一只基金「当前 43.5 分」vs「走势图今天 36.5 分」，用户看到两套结论 | 序列按日重算这两项（或让两处共用同一个 metrics builder） |

| 12  | 历史分位统一用「当前时点近 5 年分布」                      | **P2** | 早期点位带入后验信息（look-ahead）                                   | 至少把「当前分位」与「历史分位点」的窗口分离             |

## 二、现状：两条链路

### A. 实时估值（盘中）

| 数据源   | 编号  | 接口                                   | 可得字段                                | 备注                                       |
| -------- | ----- | -------------------------------------- | --------------------------------------- | ------------------------------------------ |
| 天天基金 | 1     | `FundValuationLast`（批量 JSONP）      | `gsz / gszzl / dwjz / gztime`           | 微任务合并 + TanStack Query 缓存           |
| 新浪     | 2 / 3 | `FdFundService.getEstimateNetworthPic` | `growthrate(2) / pre_nav(2)` + 分时序列 | 顺带回传当日分时                           |
| Supabase | 4     | 表 `gs_qdii`                           | 只有 `gszzl / gztime`                   | `gsz` 由 `dwjz×(1+gszzl/100)` 反推（QDII） |

准度能力现状：`useDataSourceAccuracyLabels` → `fetchBestValuationSource`（Supabase Edge Function `best-valuation-source`，未配置 Supabase 时**直接返回 null**）；今天已出净值时改在前端并发拉 1/2/3 三源、按 `|gszzl − 实际涨跌幅|` 取最小 → 「今日最准 / 昨日最准」徽标。`FundDataSourceSelector` 里另有单点「预测误差」。

→ **只有「单日最小误差」这一个瞬时判断，没有任何跨日统计**：没有 MAE、没有方向命中率、没有系统性偏差、没有误差-时间分布，也没用误差反哺选源。

### B. 持仓穿透评分（低频）

```
fetchFundValuationScore(fundCode)                        app/api/fund.js:3834
  ├─ 分类：AKTools getFundDetail + fetchRelatedSectorsBatch + refineClassificationByHoldings
  ├─ fetchHoldingsValuation                               app/api/fund.js:3341
  │    ├─ 逐只 fetchStockFundamentalsBatched(secid)  A股→AKTools stock_value_em；港美股→东财 push2
  │    └─ 权重归一到「已覆盖市值」→ 指标加权            WEIGHTED_METRIC_KEYS  app/api/fund.js:3293
  ├─ calculateHoldingsPercentiles                         app/api/fund.js:3752  （只产出 pe/pb/ps 三个分位）
  └─ calculateValuationScore                              app/lib/valuationEngine.js:299
```

关键实现细节（后面多条问题都源于此）：

- `metrics.pe = epSum > 0 ? 1 / epSum : null`，只把 `pe > 0` 的股票计入 `epSum` —— **亏损股等价于 E/P = 0**，即被当作「不产生盈利」压低整体 E/P，但**不参与任何降权或标记**。
- `calculateHoldingsPercentiles` 只处理 `pe/pb/ps`，`dividendYieldPercentile` **代码里根本不存在**。
- `buildValuationScoreSeries` 每日 metrics 硬编码 `peg: null, dividendYield: null`（`app/lib/valuationHistory.js:300-301`）。
- `confidence` 的定义就是「参与计算的指标权重合计」（`totalWeight`），**与持仓覆盖率、样本数、数据时间完全无关**。

## 三、问题清单

### 3.1 【P0】走势图与首屏分数不同源

`fetchFundValuationHistory`（`app/api/fund.js:3947`）传给序列的 fundamentals 只有 `{roe, epsGrowth, revenueGrowth}`，序列内部又强制 `peg: null, dividendYield: null`。于是任何用到 `peg` 或 `dividendYield` 权的分类，走势图的评分口径与首屏**结构性不同**。

实测（真实模块，虚构一只成长型基金、同一 reference 分布）：

```
calculateValuationScore      → 43.5 分，置信度 85%
buildValuationScoreSeries 末点 → 36.5 分，置信度 60%，metrics.peg = null
```

成长型规则里 `peg` 权重 0.25 —— 走势图直接把这 25% 权重丢掉了，分数差 7 分，置信度差 25 个点。用户在同一屏里能看到「当前 43.5」和「近 3 月走势最后一点 36.5」，属于自相矛盾。

**改法**：把「当日 metrics 组装」抽成一个函数 `buildDailyMetrics({ perStock, historyByCode, referenceByCode, fundamentals, category, date })`，首屏的「今天」也走这个函数（今天 = 序列的最后一天），从结构上消灭两套逻辑。`peg` 无法按日重算（`stock_value_em` 的 PEG 是当期值、无历史），就显式标成「当日快照值」并**在两处同样使用**，而不是在一处丢弃。

### 3.2 【P0】分位路径缺亏损守卫 → 亏损股「极度低估」

绝对值路径是有守卫的：

```js
// app/lib/valuationEngine.js:133
if (!Number.isFinite(pe) || pe <= 0) return null; // 亏损（PE 为负/0）无法用 PE 衡量
```

但分位路径没有（`app/lib/valuationEngine.js:215-223`）：

```js
if (key.endsWith('Percentile')) {
  const clamped = Math.max(0, Math.min(100, value));
  if (key === 'dividendYieldPercentile') return 100 - clamped;
  return clamped; // ← 无条件接受
}
```

而 `computePercentile`（`app/lib/valuationEngine.js:263-272`）也不剔负值：

```js
const valid = values.filter((v) => Number.isFinite(v));
```

后果：某股票近 5 年 PE 多在 10~40，今年亏损 PE = −15 → 在分布里排到最底 → `pePercentile ≈ 0~3` → 评分 3 → **判「极度低估」**。而它恰恰是最贵的一类公司。PB < 0（净资产为负）同理。

**改法**（两处都要）：

1. `computePercentile` 增加可选 `excludeNonPositive`：`pe/pb/ps` 分位一律只在该指标的历史正值子集里排名；当前值为负时直接返回 `null` 而不是分位 0。
2. 基金级：新增 `lossWeight`（见 §4.1），当亏损权重占比 > 阈值时对 PE 分位降权并在 UI 标注「含 X% 亏损仓位，PE 分位失真」。

### 3.3 【P0】同一底层数据被计两次权重

`calculateValuationScore` 里 `usePercentile` 分支的评分来源：

```js
// app/lib/valuationEngine.js:327-331
const percentileKey = `${key}Percentile`;
const percentileValue = metrics?.[percentileKey];
if (percentileValue != null) score = normalizeToScore(percentileKey, percentileValue, indicatorDef);
```

所以规则里同时出现 `{ key: 'pe', weight: 0.25, usePercentile: true }` 和 `{ key: 'pePercentile', weight: 0.25 }` 时，**两项拿到的是同一个数**。

宽基指数（`app/lib/valuationRules.js`）因此实际权重是：PE 分位 **50%**、PB 分位 15%、股息率分位 0%（永不产出）、ROE 10%、盈利增速 10%。UI 的指标表会并排显示「PE-TTM 25%」和「PE 历史分位 25%」两行几乎相同的评分，用户完全无从理解。

同样结构存在于：红利/高股息、金融、地产、REITs、债券（`dividendYield` 的 `usePercentile` 与 `dividendYieldPercentile`）—— 只因 `dividendYieldPercentile` 恒为 `null` 才暂时没有暴露出来。

**改法**：规则里**同一底层数据只允许出现一次**。两条路选一条：

- (a) 保留 `{ key: 'pe', weight: X, usePercentile: true }`，删掉独立的 `pePercentile` 项；
- (b) 保留 `pePercentile` 独立项，把 `pe` 项改成纯绝对值项并明确标注。

推荐 (b)：这样「PE 分位更便宜，但 PE 绝对值更贵」这种分歧能被看见（例如周期性行业底部 PE 高、分位低）。

### 3.4 【P1】置信度不代表「可信」，季报滞后完全隐形

`confidence = 指标权重覆盖`，而 `holdingsCoverage` 只是**并列显示**（`app/components/FundValuationPanel.jsx:132-138`）。一只基金只覆盖 30% 市值时，剩余 70% 被「假设与覆盖部分同质」，却仍可能拿到 85% 置信度。

更严重的是时效：`holdingsReportDate` / `holdingsIsLastQuarter` 由 `fetchHoldingsValuation` 一路返回了，但**估值面板不展示**（全仓只有 `app/components/FundCard/index.jsx:351` 用到 `holdingsIsLastQuarter`）。季报披露滞后一个季度本身合法，到下一期披露前最迟可滞后约 5 个月；这期间「基于持仓穿透」的结论实质上在用过时仓位。

**改法**：

```js
confidence = round( indicatorCoverage
                  × min(1, holdingsCoverage / 0.6)        // 覆盖率折扣，60% 以上不罚
                  × stalenessFactor(reportDate) )          // <3 月 1.0；3~6 月 0.8；>6 月 0.6
```

同时面板上加一行：`持仓报告期 2026Q2 · 已滞后 4 个月（下次披露 10 月底）`，超过 6 个月给黄色警示。

### 3.5 【P1】6 个分类存在永久无法评分的指标

用真实规则模块算出的「理论上限置信度」（= 规则里存在评分路径的权重合计）：

| 分类                                | 上限    | 永久缺失项（权重）                                                                                  |
| ----------------------------------- | ------- | --------------------------------------------------------------------------------------------------- |
| 债券                                | **50%** | `dividendYieldPercentile` 0.50                                                                      |
| 红利/高股息                         | **65%** | `dividendYieldPercentile` 0.30、`dividendPayoutRatio` 0.05                                          |
| 科技/AI                             | **70%** | `evSales` 0.15、`grossMargin` 0.05、`fcfMargin` 0.05、`roic` 0.05                                   |
| REITs                               | **75%** | `dividendYieldPercentile` 0.25                                                                      |
| 周期 / 地产                         | **80%** | `evEbitda` 0.20                                                                                     |
| 宽基 / 成长型 / 金融                | **85%** | `dividendYieldPercentile` 0.15 / `earningsRevision` 0.15 / `nplRatio` 0.10 + `capitalAdequacy` 0.05 |
| 医药 / 消费                         | 90%     | `fcf` 0.10                                                                                          |
| 新能源/军工/行业指数/QDII/美股/其他 | 100%    | —                                                                                                   |

注意这是**上限**：真实运行还要再打折扣（港股无 PS 分位、`stock_value_em` 偶发失败等）。债券类和红利类基本等于「半个指标在空转」，而 `normalizeToScore` 对没有评分路径的 key 一律 `return null`（注释自认「需要历史分位才能评分」）。

**改法**：见 §5「缺失指标的补源方案」。短期至少把权重让给可算指标（例如债券改用「久期 × 信用利差分位」这类代理，或直接降权重并声明「本分类指标有限」）。

### 3.6 【P1】分位样本下限过低

`MIN_PERCENTILE_SAMPLES = 30`（`app/api/fund.js:3617`）。一个上市两个月的次新股拿到 40 个样本就被当成分位，且与 5 年 1212 个样本的股票等权进入基金级加权平均。

**改法**：贝叶斯收缩（一行代码就能改，效果明显）：

```js
// k = 120 ≈ 半年交易日：样本 40 天时向 50 收缩 75%，样本 1212 天时仅收缩 9%
const shrunk = (n * rawPercentile + k * 50) / (n + k);
```

同时把 `sampleCount` 一路带到 UI（「PE 分位 42（近 5 年，n=1212）」），让用户自己判断可信度。

### 3.7 【P1】基金级 PEG 口径错误

`WEIGHTED_METRIC_KEYS` 里包含 `peg`（`app/api/fund.js:3293`），意味着一只基金的 PEG = 各持仓 PEG 的加权平均。但 PEG 是 `PE / g`，分母是增长率，**不是可加可平均的量**：一只 PE 60 / g 40（PEG 1.5）和一只 PE 10 / g 2（PEG 5）等权平均得 3.25，而组合真实 PE = 35、真实 g = 21、真实 PEG ≈ 1.67，差了近一倍。

**改法**：基金级 PEG 用聚合量重算：

```js
pegFund = weightedPE / weightedGrowth; // weightedPE 用 E/P 倒数法，weightedGrowth 用市值加权
```

`dividendYield` 加权平均是正确的（收益率可加），`roe` 加权平均也还可接受（近似可加），只有 PEG 必须改。

### 3.8 【P1】实时估值：没有误差历史，准度无法闭环

现在能回答「今天哪个源最准」，不能回答「这个源一贯准不准」。而这两件事的结论经常相反 —— 天天基金对高集中度基金常系统性高估、新浪对 QDII 常缺失、东财对主题基金常滞后。

并且选源能力依赖 Supabase Edge Function，自托管/纯本地用户（`localStorage` only 是项目主打卖点）**完全没有准度信息**。

**改法**（零外部依赖，纯本地）：

```js
// localStorage: fundValuationAccuracy
// { [code]: { [source]: [{ d: 'YYYY-MM-DD', est: 1.23, act: 1.19 }] } }  // 保留近 60 个交易日
// est = 当日 15:00 前最后一次 gszzl；act = 该日净值涨跌幅（用 navHistory，本地已有 ≈1285 天）
```

由它派生 4 个指标（见 §4.8）：`mae20`、`hitRate20`（方向命中）、`bias20`（系统偏差）、`rmse20`。用途：

1. 「今日最准」升级为「近 20 日 MAE 0.31% · 命中 17/20」；
2. 选源从「今日谁赢」改为「近 20 日 MAE 最小」（更稳，不会一天一换）；
3. `bias20` 显著且样本 ≥ 20 时给出**校准估值** `gszzl_cal = gszzl − bias20`，并标明「已按 20 日均偏差 −0.12% 校准」。

⚠️ 统计口径：必须用**涨跌幅**而非净值（分红/拆分会让净值跳变），与 `useHoldingProfit` 现有的 `(currentNav−lastNav)/lastNav` 一致。

### 3.9 【P1】估算净值与确权净值混用

`app/hooks/useHoldingProfit.js`：

```js
const profitToday = amount - amount / (1 + gzChange / 100); // 分子：估算
const exactNav = Number(fund.dwjz) || currentNav;
const amount = effectiveShare * exactNav; // 分母：确权
```

于是「当日估算收益 ÷ 总资产」的百分比既不是估算口径也不是确权口径。基金净值当天未出时，`dwjz` 是 T−1 净值，两者相差一个当日涨跌幅，量级正好和当日收益同阶。

**改法**：拆成两个字段显式表达，UI 上分开展示：

```js
marketValueNav      = share × dwjz           // 已确权市值
marketValueEstimated = share × (dwjz × (1+gzChange/100) 或 gsz)  // 估算市值
profitTodayEst      = marketValueEstimated − marketValueNav      // 估算浮盈
```

当日收益占比分母统一用 `marketValueEstimated`，并在 tooltip 说明「当日收益为估算，净值公布后自动结算」。

### 3.10 【P2】分时序列只留当日、只存净值

`app/lib/valuationTimeseries.js` 的 `recordValuation` 只存 `{time, value: gsz, date}`，且新日期一到就清空旧日期：

- 净值型纵轴在**分红/拆分日**会整段位移，看图的人会误读为「估值跳变」；
- 只有当天 240 个点，无法比较「昨天同一个时间点更便宜还是更贵」；
- 写 `localStorage` 失败只 `console.warn`，配额满时静默丢数据。

**改法**：存 `{time, gsz, gszzl, dwjz}`；作图默认纵轴用 `gszzl`（涨跌幅天然跨日可比），保留最近 5 个交易日（1200 点 ≈ 60KB，可接受）；写失败时降级为内存 Map 并提示一次。

### 3.11 【P2】无盘中时段门控、无 `gztime` 停滞检测

`useRefreshManager` 用固定 `refreshMs` 死循环刷新，只有**日级**交易日判断（`page.jsx:2389`），没有 9:15–11:30 / 13:00–15:00 的时段判断，也没有 `gsz`/`gztime` 是否推进的检测。收盘后、午休、接口卡住时都在按原频率空转；而 `gztime` 全场只在 `useHoldingProfit.js:26` 用来判断 `startsWith(todayStr)`，**从不判断分钟级新鲜度**。

**改法**：`gztime` 超过 15 分钟未推进 → 卡片标灰 + 「数据延迟 X 分钟」；连续 3 轮不推进 → 指数退避到 5 分钟；非交易时段降到 30 分钟一次（只为收盘价）。

### 3.12 【P2】分位参照带后验信息 + 阈值跨行业不可比

`app/lib/valuationHistory.js` 文件头自认：历史每日的「PE 分位」统一用**当前时点**近 5 年分布算。早期点位因此带入后验信息，走势图的历史分位是「以今天为参照的分位」，不是「当天可观测的分位」。另外 `roeToScore` / `evEbitdaToScore` 等阈值是全局常数，注释（`app/lib/valuationEngine.js:184-185`）已自认跨行业不可比。

**改法**：走势图提供两档口径（`asOf` 滚动窗口 / `anchored` 当前窗口），默认 `asOf`；行业相对分位见 §4.7。

## 四、数据指标：建议新增或修口径

### 4.1 `lossWeight` —— 亏损仓位占比（**最高性价比**，可直接从现有数据算出）

```js
lossWeight = Σ w_i  (i ∈ covered 且 pe_i <= 0 或 eps_i <= 0)   // 单位 %
```

现成数据、零成本、信息量极大：

- `> 20%` 时对 `pePercentile` 降权，UI 标注「含 23% 亏损仓位，PE 分位失真」；
- 也是给用户的最有用的风险提示之一（「便宜是因为不赚钱」）。

### 4.2 `pePercentileAdj` —— 收缩后的分位

见 §3.6。`(n·p + k·50)/(n+k)`，`k = 120`。一行代码，显著改善次新股与短窗口样本。

### 4.3 `sampleCount` + 分位置信区间

分位是二项分布估计，`n` 个样本时标准误约 `√(p(1−p)/n) × 100`。应该展示 `42 ± 3 (n=1212)`；`n < 250` 时展示 `42 ± 7 (样本不足)`。当前完全不展示，用户以为分位是精确值。

### 4.4 `dividendPayoutRatio` —— 用股息率 × PE 免费派生

```js
payoutRatio = dividendYield × pe / 100      // DY% × (P/E) / 100 = DPS/EPS
```

红利/高股息规则里这 5% 权重现在是死的（`app/lib/valuationRules.js`），用两行算术就能激活。同时它还能识别「高股息但不可持续」（payout > 100%）这类陷阱 —— 这正是红利策略最需要的信息。

### 4.5 基金级 `peg` 重算

见 §3.7。`pegFund = weightedPE / weightedGrowth`。

### 4.6 `percentileDispersion` —— 持仓分位离散度

```js
dispersion = σ({ pePercentile_i }); // 各持仓分位的标准差
```

意义：区分「整体贵/便宜」与「内部撕裂」。离散度大（如 30）说明基金是哑铃型持仓，把一个加权平均分位（如 50「合理」）呈现给用户是误导；离散度小时「合理」才真代表整体。

### 4.7 `relativePercentile` —— 相对同池的超额分位（零外部依赖）

用**已经拉到的** perStock 分位做横截面基准：

```js
peerMedian = median({ pePercentile_i | i ∈ 自选池全部持仓股票 })
relativePercentile = fundPePercentile − peerMedian
```

解决的问题：全市场都贵时，所有基金都会显示「高估」，用户无从选择。有了超额分位，可以展示「绝对分位 78（偏贵），但相对持仓池中位 62 高 16 个点」—— 这才是有决策价值的信息。**不需要任何新接口**，只需要把各基金的分位结果聚合一次（可放 `storageStore`）。

真正的行业相对分位（同行业 PE 分位）价值更高，但需要板块成分映射（`stock_board_industry_cons_em` 一类），标记为「需联调」。

### 4.8 实时侧 4 个指标（§3.8 派生）

| 指标        | 公式                                | 用途                                 |
| ----------- | ----------------------------------- | ------------------------------------ | --- | ------------------- |
| `mae20`     | `mean(                              | est − act                            | )`  | 徽标文案 + 选源依据 |
| `hitRate20` | `count(sign(est) == sign(act)) / n` | 方向可信度（用户真正关心涨跌方向）   |
| `bias20`    | `mean(est − act)`                   | 系统性偏差 → 校准估值                |
| `rmse20`    | `sqrt(mean((est−act)²))`            | 惩罚大偏差（`mae20` 会掩盖偶发大错） |

再加两个即时健康度指标：`stalenessMin`（`now − gztime`）与 `sourceSpread`（三源 `gszzl` 极差，极差 > 1% 说明分歧大，此时「最准」标签本身就不该信）。

### 9.1 §3.1 抽 `buildDailyMetrics`，首屏与走势图同源

问题：首屏评分与走势图末点是两套独立实现（首屏在 `fetchFundValuationScore` 里手写聚合，走势图在 `buildValuationScoreSeries` 里再写一遍）。P0-1 只把「输入」对齐了（补 `peg` / `dividendYield`），但两份「聚合逻辑」仍然并存——任何一处改动都会重新分叉。

做法：新增 `app/lib/valuationMetrics.js`，把「某一天的指标组装」抽成一个纯函数：

```js
buildDailyMetrics({ stocks, resolveValue, referenceByCode, snapshot, minSamples })
  → { metrics, coveredWeight, normSum, percents, samples, dispersion, lossWeight, perStockPercents }
```

- PE 走 E/P 倒数法（`epSum += w / normSum / pe`，再取倒数），不是算术加权——算术加权会系统性高估低 PE 股票的权重，1/(0.5/10+0.5/20)=13.33 vs (10+20)/2=15。
- `pb` / `ps` 按「有该指标的持仓权重」归一，缺失值不拉低均值。
- `peg` / `dividendYield` / `dividendPayoutRatio` / `roe` / 增速由 `snapshot` 带入：这些是「当期快照」，`stock_value_em` 不提供历史序列，无法按日重算，因此两处共用同一份快照值（这本身就是「同源」的前提）。
- 分位用 `percentileStat(referenceValues, currentValue)`，内部仍是「60 样本门槛 + 向 50 收缩」。

接线：

- `app/api/fund.js`：`calculateHoldingsPercentiles` → `calculateHoldingsValuationMetrics(perStock, onJobProgress)`，内部 `ensureHoldingsValuationHistory` → 新增的 `buildValuationHistoryInputs(stocks, { aWindowBySymbol, hkSeriesByKey, cutoff })`（原本 60 行内联循环，被首屏与走势图各复制一份）→ `buildDailyMetrics`。
- `fetchFundValuationScore` 第 3 步改为直接采信 `dailyMetrics.daily.metrics`，并显式覆盖 `pe/pb/ps/*Percentile` 六个键——否则会出现「分位按 A+HK 算、PE 按 A+HK+US 算」的半个口径。
- `app/lib/valuationHistory.js` 的 `buildValuationScoreSeries` 改为「逐股 `normalizePoints` → 每个日期调 `buildDailyMetrics` → `calculateValuationScore`」，`MIN_REFERENCE_SAMPLES` / `PERCENTILE_METRIC_KEYS` 从 `valuationMetrics.js` 导入并 re-export（单一来源）。

结果：首屏分数与走势图末点在实现上只剩一份聚合代码，`valuationHistory.test.js` 的「末点分数与首屏同源」护栏继续有效。

补充的一处口径修正：走势图原先只回放「有估值历史」的持仓（A 股 / 港股），美股持仓被直接过滤掉，而首屏的 PE/PB 加权是含美股的——QDII 类基金因此仍有分叉。现在改为：序列里保留全部持仓，没有历史源的（美股）用当前穿透值按常量处理（`quoteByCode`），并且**只对「完全没有序列」的股票兜底**——A/港股某天没数据时仍返回 `null`，绝不拿今天的数据回填过去（那是前视偏差）。

### 9.2 §4.6 持仓分位离散度 `dispersion`

`dispersion[metric] = σ({ 该持仓的 raw 分位 })`，`describeDispersion()` 分三档：`concentrated`(<15) / `mixed`(<28) / `split`(≥28)。

**关键教训（自查发现的自身缺陷）**：第一版用收缩后的分位算 σ，而收缩把分位压进 25~75，σ 理论上限只有 25 → `split` 阈值 28 永远不可能触发，功能等于没写。改为用 `percentileStat` 同时返回的 `raw`（未收缩分位）计算离散度：收缩是为了「基金级均值」的稳定性，不该抹掉持仓之间的真实差异。

现在「一半股票 20 倍（全 10 倍）、一半 5 倍」得到 `dispersion.pe = 50` → `split`，而加权均值分位仍是 50（看起来「合理」）——这正是要暴露的哑铃型持仓。

面板新增 `StructureNote` 一排提示：`持仓估值撕裂（σ=50）` / `亏损仓位 30%（不计分位）` / `比自选池贵 12pt`。

### 9.3 §4.7 相对自选池分位 `relativePercentile`

新增 `app/lib/valuationPeerPool.js`：每次算完一只基金的估值，把「该基金持仓的逐股 PE 分位」写进 `storageStore`（键 `valuationPeerPool`），再取池内全部股票分位的中位数：

```js
peerMedian = median({ pePercentile_i | i ∈ 自选池全部持仓股票 })
relativePercentile = fundPePercentile − peerMedian
```

- 零外部依赖：数据全部来自已经算好的分位结果，只多一次聚合并读。
- 上限 200 只基金 / 45 天过期（按 `updatedAt` 淘汰），避免池子被历史持仓污染。
- 存储通过 `bindPeerPoolStorage(storageStore)` 注入，符合项目「localStorage 只走 storageStore」的约定（`app/api/fund.js` 模块顶部绑定一次）。

局限：冷启动（新用户、或长期没刷新）时池子为空，`relativePercentile` 为 `null`，面板不显示该标签——这是刻意的降级，不猜。

### 10.3 §4.8 误差统计与校准估值

`app/lib/valuationAccuracy.js` 在原「全历史 MAE/bias/命中率」之外补齐：

- `ACCURACY_WINDOW = 20`：`summary.recent` 只统计最近 20 个**已配对**样本（近期表现比全历史更能预测今天）；
- `rmse` 与 `mae` 并列（同样的 bias 下，误差波动大的源不可信）；
- `pending` 计数：今天已记估算、尚未拿到确权净值的样本数；
- `calibrateEstimate(estimate, summary)`：窗口样本 ≥ `ACCURACY_CALIBRATION_MIN_SAMPLES = 20` 且 `|bias| ≥ ACCURACY_BIAS_THRESHOLD = 0.15pt` 才给出 `estimate − bias`；`reason` 区分 `invalid` / `no-data` / `insufficient` / `not-significant`。阈值不是拍脑袋：0.15pt 以下的偏差属于估值口径噪声，硬校准反而把噪声当信号。
- `sourceSpread`：三个数据源的 `gszzl` 极差，>1pt 时说明它们自己都没对齐，「最准」标签不可信 —— 在数据源选择器里直接显示「三源分歧 X pt」。

UI：`FundCard` 的估算涨幅在有校准时加 Tooltip「已按近 N 日均偏差 ±x% 校准：±y%」；`FundDataSourceSelector` 显示「近 20 日（N 个样本）：平均误差 / RMSE / 方向命中」「全历史 N 日平均误差 + 今日待配对 N 笔」。

### 10.4 股息率分位：真源不存在，改用价格倒推（并留下替换点）

§五 原计划用 `stock_a_indicator_lg`（AKShare 个股市值/股息率历史，一只股票一次请求即可拿到聚合估值 + 股息率）。实测两条路径都不通：

| 探针                                                                                                                                    | 结果                                                                                                                                                                                     |
| --------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET http://100.68.218.28:18081/api/public/stock_a_indicator_lg?symbol=sz000001`                                                        | **404**，响应 `{"error":"未找到该接口，请升级 AKShare 到最新版本…"}`（AKTools 未暴露该接口）                                                                                             |
| `GET https://datacenter-web.eastmoney.com/api/data/v1/get?reportName=RPT_VALUEANALYSIS_DET&columns=ALL&filter=(SECURITY_CODE="000001")` | 200，单行 22 字段（`CLOSE_PRICE`/`PE_TTM`/`PE_LAR`/`PB_MRQ`/`PS_TTM`/`PEG_CAR`/`TRADE_DATE`…），**没有股息率**；且 ≈600B/行，1300 行 ≈780KB，并不比现有 `stock_value_em`（~708KB）省流量 |

于是采用**价格倒推的代理口径**（`deriveDividendYieldReference`，`app/lib/valuationMetrics.js`）：

```text
DY_t = DY_now × price_now / price_t      （假设窗口内每股分红不变；DY_now 来自 push2 f126）
```

- 可接受的理由：股息率 = 每股分红 / 股价，分子按年更新、变动缓慢（分红政策调整才动），分母每天跳；5 年窗口里股价振幅远超分红变动，因此「股息率处于自身历史什么位置」这个**相对**判断成立；
- 不可接受的部分必须写明白：这是代理值，不是真实股息率历史。分红大幅提高的年份会把历史股息率低估，从而高估「现在很便宜」的程度；
- 触发条件：窗口内价格样本 ≥ `MIN_REFERENCE_SAMPLES = 60` 且当前股息率 > 0；否则整列缺席，引擎按规则表的 `absolute: true` 回退到绝对阈值 —— 缺数据不伪造，只降级；
- 落地链路：`buildTrendSeries` 的 `pick` 增加 `price`（`stock_value_em` 的行里本来就有收盘价，只是一直被丢掉）→ `buildValuationHistoryInputs` 派生 `historyByCode[code].dividendYield` 与 `referenceByCode[code].dividendYield` → `buildDailyMetrics` 的 `EXTRA_PERCENTILE_KEYS` 产出 `metrics.dividendYieldPercentile` → 规则表里红利/银行/REITs/债券的 `dividendYield`（`usePercentile: true`）自动改用分位；
- 缓存版本 `VALUE_WINDOW_CACHE_VERSION` 3 → 4：旧窗口的点没有 `price`，不提升版本会一直派生不出序列；
- 效果：红利类示例持仓 `{股息率 1.5%, 分位 8}` → 该指标得分 65 → 92，整只基金从 31 分升到 58.5 分（原先股息率分位永远是 null，50% 权重只能靠绝对阈值且经常整列缺失）；
- 替换点：等 AKTools 升级或找到真实股息率历史源（如集思录/理杏仁），只需把 `deriveDividendYieldReference` 换成真实序列，`buildDailyMetrics` 及其下游一行不用改。

引擎同时在 `details[i]` 里加了 `scoredBy: 'raw' | 'percentile'`，面板据此在「用分位评分」的行后面标「N 个样本分位」——用户能看出这一列到底是历史分位还是绝对阈值。

### 11.1 `setQueryData` 的 `staleTime` 在 v5 是死参数 → 11 处手写缓存全部按 5 分钟算（P0）

- **症状**：盘中 30 秒轮询却拿到 5 分钟前的估值；`valuationTimeseries.recordValuation` 按 `(date, time)` 去重，于是分时曲线出现整齐的 5 分钟台阶；`useRefreshManager` 的停滞检测恰好第 3 轮退避到 5 分钟，把问题彻底掩盖成「看起来正常」。

### 12.1 交易日历：加载失败不再毒化缓存

`app/lib/tradingCalendar.js` 原实现在 `catch` 里 `yearCache.set(year, new Set())`——一次 CDN 抖动就会让**这一整年**都按「每个工作日都是交易日」计算：延迟确认基金的持有天数（`countTradingDaysBetween`）、收益补录的逐日循环、`useTradingDay` 的判断全部静默偏移，而且进程内再也修不回来（缓存已命中，不会重试）。

现在：

- 只有**加载成功**才写 `yearCache`；失败返回 `null`，60 秒退避（`yearRetryAfter`）后允许重试；
- 新增 `yearInFlight` 做并发去重：同一年的多个调用方共用同一个请求（`isTradingDay` 在多处被并发调用）；
- **空集合视为异常响应**（正常年份至少有春节/国庆）→ `throw`，不落缓存；
- 新增导出 `hasHolidayData(year)`，让调用方能区分「确认非交易日」与「数据没加载、只能按周末退化的猜测」；
- `isTradingDay` 的 JSDoc 明确写出退化行为，避免以后误用。

### 12.2 市场日期固定北京时间（原来跟随浏览器时区）

`app/lib/fundHelpers.js` 的 `TZ` 来自 `Intl.DateTimeFormat().resolvedOptions().timeZone`，`formatDate()` 因此返回**浏览器本地日期**。但「净值更新到哪一天」「今天是几号」「15:00 截止」都是**市场语义**，必须按 Asia/Shanghai：

- UTC-8 的用户在北京时间上午 9 点（美西前一天 17:00）拿到的 `todayStr` 仍是昨天 → 今日收益按昨天算、`isNavUpdated` 判定错、收益补录起点错一天；
- UTC+8 以东的用户则相反，会把还没到的日期当成今天。

新增 `MARKET_TZ = DEFAULT_TZ`（`Asia/Shanghai`）、`nowInMarketTz()`、`formatMarketDate()`；`formatDate` 保留为 `formatMarketDate` 的别名（既有调用点语义自动修正）。展示用的本地时间仍走 `TZ`/`nowInTz()`/`toTz()`。切换的调用点：

| 位置                                                 | 用途                                               |
| ---------------------------------------------------- | -------------------------------------------------- |
| `app/api/fund.js:68` `nowInMarketTz` → `:879` `:894` | `fetchSmartFundNetValue(-Backward)` 的「今天」上界 |
| `app/api/fund.js:3021`                               | `fetchFundHistory` 区间终点                        |
| `app/hooks/useRefreshManager.js:146` `:408`          | 刷新日快照 / 收益补录的 `todayStr`                 |
| `app/hooks/useTradingDay.js:16` `:17`                | 周末/节假日判定的「今天」与「现在」                |
| `app/components/TradeModal.jsx:51`                   | 15:00 申购截止判断                                 |

顺带说明：`formatDate('...T16:00:00.000Z')` 现在在**所有**时区都解析为北京时间的次日——这正是 `app/lib/fundMetrics.js:140-150` 记录的「pingzhongdata 时间戳是 CST 零点」那个坑的正解，之前只有 UTC+8 及以东的浏览器碰巧是对的。

### 12.3 PE 倒数法的分母改为「有 PE 的那部分权重」

`app/lib/valuationMetrics.js` 的 PE 聚合是加权调和平均：`epSum += w / normSum / pe`，最后 `pe = 1 / epSum`。分母 `normSum` 是**全体权重**，于是：

```
pe_reported = normSum / Σ(w_i / PE_i) = HM(PE) × normSum / Σw_covered
```

只要有股票亏损（PE 为负/缺失）或没取到 PE，覆盖率 < 100% 就会把整只基金的 PE 放大 `1/覆盖率`——例如一半权重无 PE 时 PE 直接翻倍，且与 PB/PS 用 `rawWeight`（覆盖权重）的口径不一致。现在改为 `epSum += w / pe; epWeight += w;` → `pe = epWeight / epSum`，即「有 PE 的那部分持仓的加权调和平均」，覆盖率信息仍由 `coveredWeight` 单独表达。

### 12.4 CAGR 按日历跨度年化 + 索提诺 ddof 对齐

`computeCagr` 原来用 `steps = adjustedIndex.length - 1` 当作「交易日数 / 252」，等价于假设序列**没有缺口**。实际净值序列一定缺（非交易日、停牌、源站缺行），300 个点跨了 299 个自然日时会被当成 1.19 年：

| 数据                             | 旧口径 | 新口径（日历年化） |
| -------------------------------- | ------ | ------------------ |
| 300 点、299 自然日、累计 +35.05% | 28.83% | 44.36%             |

新增 `yearsBetweenDates(startDate, endDate)`（365.25 天/年），`computeCagr(index, { years })` 支持显式年数、缺省才回退点数口径（既有单测与外部调用不受影响），`computeFundMetrics` 用首尾净值日期传 `years`。

同时把 `computeDownsideDeviation` 的分母从 `n` 改为 `n−1`：同一份数据里夏普分母（`annualizeVolatility`）用 ddof=1、索提诺分母用 ddof=0，两个风险调整指标不可比（n=250 时差约 0.2%，方向一致但口径必须统一）。

### 12.5 「涨幅反推收益」的分母守卫

`app/hooks/useHoldingProfit.js` 有两处 `amount - amount / (1 + rate / 100)`（无估值时的 `zzl`/`gszzl` 降级路径、`dwjz` 非法时的兜底）。`rate ≤ -100%` 时分母 ≤ 0，会产出「市值减负数」这种天文数字；源站把 `gszzl` 写成 `-100`、净值断档、单位错位成百分数都会触发。抽出 `profitFromChangeRate(amount, ratePct)`：`1 + rate/100 ≤ 0.01` 时返回 `null`（今日收益暂不可算），不再让脏数据进页面。
